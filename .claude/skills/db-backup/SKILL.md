# 데이터 백업 (읽기 전용)

코드가 쓰는 모든 테이블을 JSON으로 내려받고, 받은 행 수를 DB의 집계와 대조해 빠진 게 없는지 검증한다. DB에는 쓰기·삭제를 하지 않는다.
Supabase도 자동 백업을 하지만(공식 문서 기준 모든 플랜 매일), 무료 플랜의 보관 기간은 문서에 없고 직접 내보내기를 권장한다. 그래서 별도로 받아 둔다.
**사진 파일(Storage)은 DB 백업에 들어가지 않는다** — 이 스크립트가 사진 목록을 남기고, `--with-files`로 파일까지 받는다.

## 실행 (프로젝트 루트에서, `.env.local`의 서비스 키 필요)
```bash
# 1) 미리보기: 테이블별 행 수만 보여준다 (파일 저장 안 함)
node .claude/skills/db-backup/scripts/backup.mjs --dry-run

# 2) 백업: 프로젝트 옆 spm-backups/<날짜_시각>/ 에 테이블별 JSON + manifest.json 저장
node .claude/skills/db-backup/scripts/backup.mjs

# 3) 사진 파일까지 받기 (게시판 사진·팀 로고, 현재 약 3MB)
node .claude/skills/db-backup/scripts/backup.mjs --with-files
```
- 저장 위치는 **프로젝트(git) 밖**이어야 한다. 프로젝트 폴더 안으로 지정하면 스크립트가 거부한다 (이름·이메일 등 개인정보가 커밋될 수 있음).
- 결과에는 개인정보가 들어 있다. 외부 서비스·메신저로 공유하지 말고 내 컴퓨터에만 둔다.

## 결과 읽는 법
- `ok` — DB 집계 행 수와 받은 행 수가 같다.
- `MISMATCH` — 받은 행 수가 다르다(백업 도중 데이터가 바뀌었거나 페이지 누락). 다시 실행해서 같은 결과면 원인을 조사한다.
- `ERROR` — 그 테이블을 못 읽었다. 메시지를 확인한다.
- `WARN ... DB에 없는 테이블` — 코드에 `.from("이름")`이 있는데 DB에 그 테이블이 없다. 사진 버킷 이름(`gallery`)이면 정상이고, 아니면 **버그**다 (실제로 `/api/user/delete`가 없는 테이블을 지우다 실패하던 걸 이걸로 찾았다).

## 언제 하나
- 데이터를 대량으로 바꾸거나 지우는 작업, DB 구조 변경 전
- 사용자가 늘어난 뒤에는 정기적으로(예: 월 1회)
- 배포 전에는 필수가 아니다(코드 배포는 DB를 바꾸지 않음). DB 변경(`db-migration`)이 있을 때만.

## 복구할 때 (DB에 쓰는 작업이라 자동화하지 않았다)
스크립트는 읽기 전용이다. 복구가 필요하면 **사용자에게 먼저 확인**하고:
1. 무엇이 사라졌는지 범위를 확인한다 (어떤 테이블, 어떤 기간).
2. 먼저 Supabase 대시보드의 자체 백업(Database → Backups)에서 복원할 수 있는지 본다.
3. 일부 행만 필요하면 백업 JSON에서 해당 행을 골라 `upsert`(id 기준)로 되돌린다. 전체를 덮어쓰지 않는다.
4. 되돌린 뒤 행 수와 화면을 확인한다.

## 보고 형식
- 테이블 수, 총 행 수, `MISMATCH/ERROR/WARN` 개수
- 저장 위치와 사진 파일 포함 여부
