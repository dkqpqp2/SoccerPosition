# 운영 리포트

SPM 운영 DB(Supabase)를 **읽기 전용**으로 집계해서 사용 현황을 보여준다. 개인정보(이름·연락처)는 출력하지 않고 개수만 낸다.

## 실행 (프로젝트 루트에서)
```bash
# 전체 + 팀별 요약
node .claude/skills/ops-report/scripts/ops-report.mjs

# 한 팀 상세 (팀 id 전체)
node .claude/skills/ops-report/scripts/ops-report.mjs --team <팀id>
```
- `.env.local`의 서비스 키가 필요하다(로컬에만 있음). 쓰기·삭제는 하지 않는다.
- 기본 "내 팀" 상세는 FC키싱구라미: `0216d6ae-fcd1-4c2a-b439-4e2aad003e47`.

## 숫자를 해석할 때 (중요)
- **"사용자 수"로 쓸 값**은 `가입한 활성 팀원(용병 제외)` — 계정이 연결돼 있고 `left_at`이 없는 팀원이다. 수동 등록 용병은 계정이 없어서 사용자로 세지 않는다.
- **전체 가입자(users)·팀(teams)** 숫자는 테스트 계정·테스트 팀·가입만 하고 안 쓰는 팀이 섞여 있어서 "실사용자 수"로 말하면 안 된다. 팀별 요약에서 경기·배정이 0인 팀은 사실상 안 쓰는 팀이다.
- "최근 30일" 숫자가 0이어도 시즌 비수기일 수 있다(경기 기간을 같이 본다). 줄었다고 단정하지 말고 근거와 함께 말한다.
- 이력서·자기소개서에 쓸 숫자는 **상세 모드의 값**을 그대로 쓰고, "지인 일부가 테스트에 참여"처럼 부풀리지 않는 표현을 함께 쓴다. 제출 직전에 한 번 더 실행해서 최신 값으로 바꾼다.

## 보고 형식
1. 핵심 숫자 3~5개 (팀원 수, 경기, 배정, 회비 기록, 최근 30일 활동)
2. 눈에 띄는 변화나 이상한 점 한두 가지 (예: 최근 30일 활동 없음, 가입만 하고 안 쓰는 팀)
3. 이력서/소개에 쓸 때 주의할 점(해당할 때만)

## 지표를 늘리고 싶을 때
새 기능을 만들었으면 `scripts/ops-report.mjs`의 `teamStats()`에 `count("테이블", q => q.eq("team_id", teamId))` 한 줄을 추가한다. 새 테이블이면 팀별 `team_id` 필터를 꼭 건다(멀티 팀 격리).
